# 面向 Agent 的《上古卷轴 V：天际》MOD 开发指南

文档版本：1.0 · 编写日期：2026-09-24 · 读者：开发、维护和审查 Skyrim MOD 的 agent。

**定位：这是一份可复用的工程工作准则，不是某个补丁的固定技术方案，也不授权 agent 操作游戏、安装目录或用户存档。** 主要讨论 PC 上的记录插件、Papyrus、SKSE 原生插件、HUD 和动画集成。Classic/LE、SE/AE、VR、不同商店版本及主机平台必须分别核实能力；本文的代码路径和工具示例不能跨平台直接套用。

本项目的具体实现另见 [KratosRagePatch 模块、调试与扩展规格](kratos-rage-patch-spec.md)。该补丁锁定的 1.6.640、SKSE 2.2.3、100 点怒气等均是项目特例，不是 Skyrim MOD 的通用要求。

## 快速阅读顺序

1. 接手任务先读「工作边界」「版本矩阵」「最小实现层」。
2. 写实现前读所涉及的记录、Papyrus、原生、UI 或动画章节。
3. 出问题按「调试顺序」收集证据，不直接替换用户环境。
4. 交付前完成「分层验证」「发布与存档兼容」清单。

---

## 1. 接手任务：先把事实与权限写清楚

### 1.1 必须先回答的六个问题

- **目标是什么？** 用可观察行为表达，例如“仅在资源满足条件时进入动作”，不要把“写一个 DLL”当作需求本身。
- **实际环境是什么？** 游戏可执行文件版本、商店/发行渠道、SKSE 分支及版本、MOD 管理器、相关前置和旧存档使用情况。
- **哪些是已确认，哪些只是猜测？** 文件存在不代表加载成功；能编译不代表接口已绑定；作者描述不等于当前二进制的记录内容。
- **可以读什么、改什么、运行什么？** 工作目录、原 MOD、游戏 Data、MO2 profile、测试存档和工具启动权限分别列出。
- **最小实现层是什么？** 能用记录或现成框架解决，就不要上原生 hook；能追加独立补丁，就不要改原包。
- **完成如何验证？** 至少区分源码检查、编译、静态产物检查、隔离测试、实际游戏验收。

建议接手记录采用下列字段，不用未确认信息填空：

```text
目标行为：
不在范围内：
游戏版本 / 商店：
SKSE 与相关前置版本：
已有实现与已知问题：
允许写入目录：
禁止动作：
存档兼容目标：
验收条件与目前证据：
```

### 1.2 默认保护规则

- 原 MOD、游戏本体及第三方 SDK 按只读输入处理；需要修补时优先输出独立 MOD，保留回退路径。
- 没有明确授权，不启动游戏、不附加调试器、不修改 profile/INI/加载顺序、不安装、不清理存档、不运行行为生成器。
- 用户正在测试某个版本时，**冻结该发行包及校验文件**。新文档可以单独新增，修复版本使用新版本号/新文件名；不暗中替换同名 ZIP。
- 原文件基线应记录相对路径、数量和 SHA-256；检测到变化先解释，不用新基线掩盖差异。
- 不把报错清零等同于修复：不要通过吞异常、跳过测试、关闭前置检查或移除原条件来“让它能跑”。
- 是否初始化/提交 Git、是否安装工具，遵循所在项目与用户的实际授权，不能从本文推导权限。

## 2. 版本矩阵：不要用“AE”三个字代替兼容性声明

### 2.1 至少记录这些维度

| 维度 | 必须具体到 |
| --- | --- |
| 游戏 | 可执行文件版本；必要时加文件哈希 |
| 发行渠道 | Steam、GOG 等，不从目录名字推断 |
| SKSE | 对应该 runtime 的发行包版本 |
| 原生地址依赖 | Address Library 分支及是否覆盖目标版本 |
| 编译目标 | x86/x64、结构布局分支、编译器 ABI、运行库 |
| 记录与资源 | 插件格式、ESL 能力、脚本/动画/模型的目标版本 |
| 第三方前置 | 精确版本或经过验证的兼容范围 |

“拥有 Anniversary Upgrade 内容”“运行 1.6 系列可执行文件”“安装了名为 SE 的游戏”是不同概念。插件作者应以实际 executable/runtime 为准。LE 的 32 位 DLL 不能变成 SE 的 64 位 DLL；SE、VR 的地址和结构也不能默认相同。

上游会更新：SKSE 官网为不同 runtime/渠道列出不同构建。**不要把“官网下载最新”写成对旧版本的修复方案。** 首次适配、目标版本变化或依赖升级时，重新查看官方支持表并锁定依赖。

CommonLibSSE-NG 提供多 runtime 支持能力，不意味着任意使用它的插件天然兼容所有 runtime。导出元数据、结构布局、relocation ID、hook 目标、功能分支及每个目标的测试都必须成立。Address Library 解决部分地址定位问题，不替你保证 ABI、行为和 hook 契约。

### 2.2 环境调查不能代替用户决定

可只读获取可执行文件版本、现有配置、原 MOD 记录和依赖清单。但对于未确认的新项目，不要因为机器上已有某个游戏目录就选定平台，也不要擅自升级/降级游戏以迎合当前代码。

## 3. 先复用成熟工具，再选择最小实现层

在目标平台确认后，先搜索官方文档和现成项目/库，记录候选项目的许可、维护状态、版本范围与缺口。没有必要重复实现 ESP 读写器、UI 注册协议或行为生成器。

| 需求类型 | 优先考虑 | 不应默认引入 |
| --- | --- | --- |
| 装备、法术、任务、效果或条件变更 | Creation Kit、xEdit、Mutagen 生成独立记录补丁 | 原生 hook |
| 稀疏事件与任务生命周期 | Papyrus、已有事件扩展 | 每帧轮询 |
| 高频事件、严格事务、复杂状态或原生能力 | SKSE + 成熟 CommonLib 分支 | 手写跨版本偏移与地址扫描 |
| HUD/菜单显示 | 对应游戏 UI 的 Scaleform/SkyUI 等框架 | 浏览器页面当作原生 HUD 成品 |
| 条件动画替换 | 目标版本可用的 OAR 等框架 | 重做整套行为图 |
| 动画事件载荷 | 原框架和现有载荷解释器 | 重复施放原效果 |
| 必須修改行为图/新增行为 | 对应生态的行为工具及其文档 | “所有动作 MOD 都重跑行为生成器” |
| 批量分发或规则配置 | 已有分发器/补丁框架 | 为单个静态分配写 DLL |

选择一个能闭合需求的最小组合，说明为什么更轻的方案不足。对已有工程，优先延续已确认方案；技术栈替换是另一个决策，不伪装成顺手整理。

## 4. 项目组织与可重复构建

推荐将输入、源码、生成物和发行物分开：

```text
project/
  src/                 原生代码（若需要）
  papyrus/             自己的 PSC
  ui/src/              UI 源码（若需要）
  data/                配置模板、人工核实的记录事实
  tools/               构建、检查、打包程序
  tests/               规则测试、跨层契约与固定夹具
  docs/                规格、构建记录、已知限制
  vendor/              锁定版本的源码/编译 SDK；不直接发行
  build/               编译输出、日志、报告、隔离测试
  build/stage/         预期进入虚拟 Data 的文件
  dist/                不可变发行包和校验文件
```

这只是建议，不要求为纯 ESP 小补丁创建全部目录。已有结构合理时保持原样。

构建要点：

- 依赖版本固定到 release/tag/commit，记录下载来源与校验值；不要运行未经理解的安装脚本。
- SDK 头文件与运行时依赖分开：有 `SomeAPI.psc` 仅表示可以编译，不表示用户运行时有实现。
- `Debug`、`Release`、工具链 ABI 和 `/MD`/`/MT` 要一致；发行依赖哪些 VC 运行库，应由最终 DLL 导入表确认。
- 日志记录完整命令、退出码、工具版本和输入路径。路径有空格和中文时正确引用，不靠改变用户当前目录碰运气。
- 构建输出留在工程内，不把系统级 `install` 当作普通构建步骤。
- 动手前检查生成目录是否真是生成物；不要递归删除未知目录。自建副本、快照或独立构建目录比覆盖用户文件更容易回退。
- 新建运行时文件要同步打包白名单。只修 stage 不改生成器，会在下次构建时丢失修复。

## 5. 记录插件：FormID、masters、VMAD 与 SEQ

### 5.1 始终分清四类标识

1. **EditorID**：人类可读名称，不应视为任意上下文都唯一的运行时定位接口。
2. **所属插件 + local FormID**：适合描述固定记录依赖。
3. **插件文件中的 FormID**：高位索引对应该文件的 master 映射，不能直接当运行时加载索引。
4. **运行时 FormID**：受加载顺序和 light-plugin 映射影响，不应从一次日志硬编码到其他机器。

在 C++ 使用支持“插件名 + local ID”的解析接口，在 Mutagen 使用 `FormKey` 等成熟表示。新记录和对原记录的 override 要明确区分：复制新记录与覆盖原记录的兼容/分发意义不同。

### 5.2 ESL 不是一个随手勾上的标志

是否适合 ESL 要依据目标 runtime、记录范围、记录类型和当前工具能力。不同游戏版本对 light 插件能力存在差异；面向旧 SE 版本常采用新记录 `0x800–0xFFF` 的保守区间，但不能把它写成所有新版环境的唯一规则。

已发布插件不要随意 compact FormID。旧存档、脚本属性、外部配置和其他补丁可能都引用旧 ID。改 ID/插件名/序列化标识属于迁移问题，不是格式清理。

### 5.3 显式 masters 不等于完整运行前置

记录文件可能只引用两个 ESM，但 DLL 按名称动态查找另一个 ESP，Papyrus 又依赖某个扩展插件。安装说明需分别列出：

- 记录层 masters；
- 原生运行依赖；
- Papyrus 运行依赖；
- UI/动画/载荷框架；
- 必须保留的原 MOD 资源。

不要按文档里的枚举顺序推断磁盘 master 顺序。让成熟写入器维护引用，写完后反解析，并核对关键跨 master 的引用是否正确。

### 5.4 生成后至少核对什么

- TES4 标志、格式/版本、新记录 ID 和 EditorID、引用与 masters。
- SPEL 的类型、施放方式、目标方式、cost、effect 列表；MGEF 的 archetype、flags、持续/范围和脚本。
- QUST 启动方式、alias 填充方式，以及脚本的实际 VMAD 绑定。
- VMAD 属性名称、类型、目标记录；form 属性与 alias 属性不能混写。
- 需要 start-game-enabled quest 时，确认目标环境需要的 SEQ，并用成熟工具生成/反查。不要把某次运行的 `FE...` 或加载索引写成固定 SEQ 值。
- 用 xEdit/Mutagen 回读，再对高风险字段作独立检查。**同一工具读回自己写出的文件只证明部分自洽，不是游戏验收。**

不要手工拼 ESP 二进制作为首选生产路径。若测试中写了最小解析器，要清楚其支持范围；它不应冒充完整格式验证器。

## 6. Papyrus：生命周期比语法更容易出错

### 6.1 编译与绑定

- `.psc` 是源码，运行游戏需要 `.pex`。编译器、flags、import 路径与继承脚本必须匹配目标环境。
- 只把自己的 PEX 放进补丁；不要把整个 SDK 编译目录打包，意外覆盖 SkyUI、SKSE 或原版脚本。
- Native 函数必须同时对齐：PSC 声明、C++ 注册脚本名、函数名、参数顺序/类型、返回值和 global/member 属性。
- 编译通过不代表 native 已注册，也不代表 VMAD 属性不为 None。反汇编和对象绑定检查应成为构建的一部分。
- Papyrus 标识符大小写不敏感，要注意与内置 Form 类型、继承属性重名。

### 6.2 初始化、读档与 UI 重建分别处理

`OnInit` 不是“每次载入存档都会执行”的替代物。玩家 alias 的读档事件、SKSE 消息和框架自己的 reload/reset 回调各有职责。

建议遵守：

- 注册事件可重复执行，但不叠加；只取消自己的注册，不清空其他 MOD 共用对象上的全部订阅。
- 明确哪些注册、计时器、UI 实例需要在读档后恢复，不将其存活假设混入持久状态。
- 尽量事件驱动；必须轮询时使用有生命周期边界、可终止且防重复的单次更新链。
- “注册一次单发更新”不代表严格定时。VM 负载下可能延迟，状态机必须容忍。
- UI 未就绪时缓存可重放的状态；一次性反馈是否丢弃、排队或重播，要作为契约说明。
- `Utility.Wait`、外部 native 和 ModEvent 都不是同步事务的凭据。确认效果发生后再提交不可逆的资源变化。

### 6.3 配置与日志

JSON 的普通键值 API 与路径 API 可能语义不同。对于嵌套手写 JSON，应核实实际库的读取约定，不凭函数名称猜测。默认值、模板、读取路径、验证范围和下推参数要可自动对照。

同时区分：字段缺失、文件解析失败、越界回退和下游再次钳制。若 Papyrus 接受 60 秒但原生只允许 5 秒，应文档化实际结果，不能只列第一层范围。

`Debug.Trace` 进入 Papyrus 日志的前提是有效配置启用了相应日志；路径与 INI 可能被 MOD 管理器重定向。日志默认不开启不代表脚本没有执行，也不要为了日志擅改用户配置。Papyrus 日志并非原生崩溃转储。

## 7. SKSE 原生插件：规则与引擎适配必须分层

### 7.1 建议的职责边界

- **入口层**：版本/运行时校验、日志初始化、Papyrus/消息/序列化注册。
- **桥接层**：查找游戏记录、接收事件、资格/来源判定、安排引擎线程任务、驱动规则。
- **纯规则层**：数值、去重、速率预算、事务和存档逻辑，不直接依赖 `RE::Actor` 等引擎对象。
- **显示层**：只读取快照，不单独持有另一份权威数值。

先查询成熟 API；仅在现有事件/接口不满足需求且确有版本证据时考虑 hook。hook 要验证目标地址/签名、长度、调用约定及卸载/失败行为，不能把“成功编译跳板”当作兼容性证据。

### 7.2 线程、对象寿命与队列

- Papyrus、SKSE 回调和引擎事件的执行上下文不同。互斥锁只保护自己的数据，不会自动让引擎 API 变得线程安全。
- 将需要游戏线程的操作投递到合适任务接口。**`AddTask` 表示排队，不保证下一帧，也不是延时计时器。**
- 延迟任务不要捕获可能失效的裸 Actor 指针；按 SDK 契约使用 handle、ID 或重新查找，执行时再次验证。
- Restore/Revert 后取消或隔离旧任务。generation/epoch 是一种简单做法：入队捕获代数，执行时若世界已更换则丢弃。
- 别在跨存档状态里存对象指针、绝对内存地址、旧 token 或挂起闭包。

### 7.3 事件必须按真实语义解读

命中、投射物命中、魔法命中、死亡和击杀不是同一事件。多个来源可能报告同一次攻击；动画发出“攻击”也不等于打中了敌人。

先弄清：

- 事件由谁产生、source 是武器/Spell/Projectile/引用中的哪一种；
- flags 的版本来源与位含义；
- 格挡、友军、自己召唤物、尸体、持续伤害、AOE 多目标如何处理；
- 致命一击与死亡事件可能的先后顺序；
- 去重键、去重通道、时间窗口、预算是否所有来源共享。

数据驱动时采用审核过的白名单或明确规则。自动分析得到的“带伤害记录”列表是候选，不应直接认定为可计分攻击。

### 7.4 事务与存档

典型状态转换应写清楚：可用 → 满足条件 → pending → 确认成功/取消。失败不消耗的需求，优先实现“确认后扣除”，不是先扣再赌一定能退。

co-save 设计至少包含唯一插件标识、record type、schema version、长度/范围验证。长期引用需要适当的 FormID 恢复机制；纯数值可采用更简单的结构。记录版本改变应增加迁移/拒绝旧记录策略，而不是静默换布局。

正常加载不应重放一次性满额提示；配置到达晚于恢复时，不能用临时默认上限永久截断合法存档值。重复 load/reconcile 回调须幂等，但“幂等”不能靠每次都清空新产生的 pending 状态来实现。

## 8. HUD、动画和外部资源

### 8.1 Skyrim HUD 不是浏览器页面

Skyrim HUD 的 Scaleform/AVM1 与现代 Web/AS3 不是同一运行环境。确认 SWF 版本、ActionScript 版本、根 clip 协议和宿主提供的方法。SkyUI widget 还需要它自己的注册/重载契约。

- 逻辑坐标不一定是显示器像素；明确基准尺寸、锚点、缩放和透明度单位。
- 逻辑上的显隐、宿主 HUD 模式显隐、SWF `_visible`、alpha 动画是不同层次。
- 暂时闪烁/渐隐需明确取消与重建恢复逻辑，避免多个 `onEnterFrame` 处理器相互覆盖。
- HUD 不应决定资源是否消费或变身是否成功。
- 编译和 SWF tag/字符串检查不等于视觉正确。浏览器/Flash 模拟器只能补充调试，不能替代实际 Scaleform 验收。

### 8.2 OAR 与载荷集成

- 先确认目标 OAR 版本的配置格式、目录解析、优先级和条件语义，不凭旧 DAR 经验拼 JSON。
- 添加门槛时保留原装备、方向、按键和排他条件；不能为了让新条件生效删除旧条件。
- 复用原动画时优先使用框架公开的目录复用能力；不要未经许可重新分发 HKX。
- 整文件覆盖的 JSON/INI 在 MO2 中只能有一个冲突胜出者。记录覆盖范围和人工合并需求，不能声称“放后面就兼容所有补丁”。
- 载荷移交给新实现时维护表格：原行、真实 Form 类型、参数、保留/替换/移除、由谁执行。防止两个层各施放一次。
- 不因“SpellType 是 Ability”就武断认定无法施放；检查实际调用的解释器/API 语义。反过来，MGEF 也不能当作 SPEL 随意替换成额外效果。
- 只改条件或配置不一定需要重跑行为生成器。是否需要取决于实际行为文件变化及所用框架。

## 9. 调试顺序：从证据最便宜的边界开始

### 9.1 先确认用户测的是哪个文件

收集发行 ZIP/DLL/PEX 的版本或哈希、runtime、前置版本、症状发生时间与最小复现步骤。确认 MO2 虚拟 Data 中**实际胜出的文件**，不是只看工程目录已编译的文件。

MO2 左侧文件优先级与右侧 ESP 加载顺序是两回事。工具绕过 MO2 启动时，通常看不到相同的虚拟文件集合。核对配置来自原 MOD、补丁、Overwrite 还是另一个覆盖包。

### 9.2 推荐排查层次

1. **加载层**：版本匹配、缺失 DLL 导入、SKSE loader 日志、插件自身日志、注册/记录解析成功证据。
2. **记录层**：ESP 启用、masters/动态依赖、alias/VMAD/SEQ、实际 Form 类型。
3. **脚本层**：PEX 胜出文件、native 绑定、事件签名和注册、读档回调、None 属性、JSON 读取。
4. **规则层**：事件输入、资格、来源分类、去重、共享预算、pending/确认/取消。
5. **集成层**：OAR 条件/优先级、PI 实际载荷、其他补丁重复执行或覆盖。
6. **显示层**：真实数值与 HUD 是否一致、widget 是否 ready、显示模式、坐标/缩放/动画。

日志缺失时先问“这条路径是否本来就记录日志”。没有加怒日志不能推出没有计分；一个成功加载 log 也不能推出所有脚本和前置已正常工作。

### 9.3 临时诊断的约束

- 有现成日志/只读 getter 就先用；需要新诊断包时独立版本标识，保留原测试包。
- 建议记录：事件种类、来源 plugin/local ID、目标标识、前后快照、拒绝原因、token/generation 和时间。限流，避免逐帧刷盘。
- 原生崩溃使用匹配的 PDB、构建哈希和兼容的 crash logger/调试器；调用栈里的模块名只是线索，不是责任结论。
- 不能假设存在 `SetRage`、MCM 调试开关或自定义控制台命令。通用 Skyrim 控制台也不能任意直接调用全部 global Papyrus 函数。
- 最小复现改变一个变量。不要同时升级 SKSE、改排序、改配置和清存档后再声称某个代码改动有效。

## 10. 分层验证：每种证据证明什么

| 层次 | 可证明 | 不能单独证明 |
| --- | --- | --- |
| 语法/类型检查 | 语法、签名和编译期约束 | 游戏里加载/绑定成功 |
| 原生产物静态检查 | PE 架构、导出、依赖、元数据 | hook/引擎调用可用 |
| ESP/PEX/SWF 反解析 | 指定字段、接口、资源结构 | 生命周期、动画和视觉效果 |
| 纯规则单测 | 数值、边界、事务、序列化行为 | RE/SKSE 事件本身真实语义 |
| mock 集成 | 当前真实业务源码在模拟接口下的链路 | 游戏线程调度、VM 延迟、真实对象寿命 |
| 实际游戏验收 | 已测试环境与步骤中的行为 | 未测试版本和任意整合包的兼容性 |

测试设计最低建议：

- 正常输入、边界输入、无效输入和失败路径；重复事件与乱序事件。
- 同帧队列 drain、延迟确认、超时取消、重复 reconcile、跨读档旧任务。
- 配置缺失/坏 JSON/越界/自定义上限；状态保存恢复及旧 schema。
- 生成物的独立回读与跨文件接口集合比较。
- 不让 fixture 互相污染；mock 测真实源码，不抄一份业务实现让它自测。
- 负向探针的“预期拒绝”与生产测试失败分别记录，不用模糊的“全绿”藏掉失败/跳过。

真实运行验收只能在授权的测试环境中进行。未获授权时交付离线证据、测试包和用户验收清单，明确未验证的部分。

## 11. 发布、版本与存档兼容

### 11.1 发行检查

- 使用 Data-root 布局；哪些文件需要赢冲突，清单应精确到路径。
- staging 采用明确白名单，禁止将 SDK、工具、第三方 DLL、缓存、PDB、原 MOD 资源随手打包。需要分发的资源单独核许可。
- 附带依赖说明、支持 runtime、安装顺序、配置路径、回退办法、已知限制、实际验证记录和许可证。
- ZIP 内清单记录每个文件大小/SHA-256；ZIP 外保存整体哈希。清单不对自己作递归哈希。
- 重新打开 ZIP 检查 CRC、条目集合、路径安全、大小写冲突和字节一致；仅“压缩命令退出 0”不足以完成发布。
- 验证脚本应可重跑，命令及所需输入清楚。对“当前工作树”比较的审计会因后续文档变更而失败：这与老 ZIP 被损坏是不同结论。
- 同名包拒绝覆盖。复现某次用户问题要有该包的精确源码/符号/构建信息，不只保留最新源码。

### 11.2 存档安全

`.ess`、同名 `.skse`、脚本状态和依赖加载状态共同影响结果。未做迁移验证就不要承诺“随时热卸载”“旧档无风险”。

安全回退通常是禁用独立补丁，并恢复安装前配套备份的测试存档与 co-save；是否足够仍取决于项目。不要自动使用存档清理器，或通过删除脚本实例来掩盖状态机错误。

变更风险至少审查：记录 ID、插件名、script/class 名、VMAD 属性、native ABI、序列化 ID/version、OAR 文件夹名、配置键和持久化语义。对于用户正在测试的版本，文档更新与运行时更新分开交付。
